# ЦЕЛЬ ЭТАПА

Создать внутри **Vernatun Console** полноценный технический контур управления платформой:

**Platform Operations Center**

Он предназначен только для:

- `platform_admin`;
- при необходимости — отдельной будущей технической роли `platform_engineer`.

Этот раздел НЕ должен быть доступен:

- org_admin;
- manager;
- dispatcher;
- accountant;
- resident;
- owner;
- renter;
- family;
- contractor;
- security;
- обычному support без специального permission.

Основная задача:

сделать Vernatun не просто приложением, а **управляемой SaaS-платформой**, которую можно обслуживать, резервировать, диагностировать, интегрировать, расширять модулями и обновлять через контролируемый administrative workflow.

# 5. BACKUP CENTER

Добавить:

`/console/system/backups`

Это один из самых важных технических разделов.

Поддержать несколько типов backup.

---

# 5.1 DATABASE BACKUP

Тип:

**Database Only**

Создавать backup PostgreSQL.

Предпочтительно использовать стандартный:

`pg_dump`

Backup должен содержать:

- schema;
- migrations state;
- business records.

Не включать plaintext secrets.

---

# 5.2 FILES BACKUP

Тип:

**Files Only**

Включить:

- private photos;
- private documents;
- uploaded assets;
- organization logos;
- другие user-generated files.

Не включать cache/temp.

---

# 5.3 FULL APPLICATION DATA BACKUP

Тип:

**Full Data Backup**

Включает:

- PostgreSQL;
- private uploaded files;
- storage metadata;
- application metadata необходимую для восстановления.

---

# 5.4 PLATFORM CONFIGURATION BACKUP

Тип:

**Configuration Backup**

Можно включать:

- non-secret settings;
- organization module configuration;
- plans;
- system configuration;
- integration definitions WITHOUT secret credentials.

Нельзя экспортировать secret values открытым текстом.

---

# 5.5 FULL SYSTEM PACKAGE

Если архитектура позволяет безопасно:

**Full Platform Snapshot**

может включать:

- DB backup;
- private files;
- current application version manifest;
- migration version;
- module registry;
- integration registry;
- checksum manifest.

Не надо включать:

- node_modules;
- build cache;
- temp;
- logs;
- raw environment secrets.

# 82. ВАЖНО ДЛЯ REPLIT

Сейчас проект работает в Replit.

Поэтому перед реализацией backup/update functionality отдельно выясни ограничения Replit runtime:

- writable filesystem;
- persistence;
- deployment filesystem;
- process restart;
- environment secrets;
- PostgreSQL access;
- storage persistence.

Не проектируй update mechanism, который работает локально, но физически не может безопасно работать в текущем Replit deployment.

Если Replit deployment не позволяет безопасно заменять application files runtime-обновлением:

НЕ имитируй это.

В таком случае:

реализуй Update Center как:

- upload;
- validation;
- manifest;
- history;
- backup;
- staged state;

а installation adapter сделай deployment-provider-specific.

Статус:

`Manual deployment required`

Это лучше ложной кнопки обновления.
