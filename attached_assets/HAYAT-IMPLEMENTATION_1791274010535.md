# HAYAT by Vernatun — реализация 30 сентября 2026

## Результат и границы

Создана отдельная рабочая оболочка HAYAT в существующем React / Vite приложении. Это **работающая адаптивная web-версия с общим backend**, а не готовые сборки App Store / Google Play и не полное выполнение всех 37 разделов исходного ТЗ.

Основные референсы: №1 — HAYAT; №5 — охрана; №6 — техник; №7 — подрядчик. №2–4 относятся к жильцам ImTun. Данные из изображений не выдаются за реальные записи базы. Карточки показывают существующие записи, поэтому имена, номера и язык пользовательского содержимого могут отличаться от макетов.

## Аудит и повторное использование

- React 19, TypeScript, Vite, Lucide; Express, PostgreSQL, серверные сессии и CSRF.
- Общие users, memberships, role_assignments, organizations, buildings, units, module_entitlements.
- ResidentRequest и WorkOrder уже разделены: work_orders.request_id с ограничением UNIQUE — один наряд на заявку в текущей модели.
- Существуют defects, visitor_passes, access_events, incidents, assets, maintenance_plans, закрытые фотографии/документы, аудит и уведомления.
- Переходы работ и дефектов уже проверяются сервером; версии защищают от перезаписи устаревшего состояния. Для работ используются ключи идемпотентности.
- В Workflow существуют локальные черновики отчёта и чек-листа, изолированные по assignment/context ID и request ID. Автоматической синхронизации и service worker нет.
- Существующие ImTun, Vernatun OS, вход, выбор контекста, MFA и серверные процессы сохранены.

Основные маршруты: `/hayat/management`, `/hayat/dispatch`, `/hayat/my-work`, `/hayat/contractor`, `/hayat/security`. Общие: `/hayat/works`, `/hayat/assets`, `/hayat/documents`, `/hayat/announcements`, `/hayat/meetings`, `/hayat/notifications`, `/hayat/properties`, `/hayat/units`, `/hayat/people`, `/hayat/events`, `/hayat/incidents`, `/hayat/settings`. Видимость зависит от роли, модулей и прав. Карточки используют `requestId` или `defectId` в URL, затем сервер повторно проверяет доступ.

## API и БД

Новый `GET /api/hayat/queue?search=&status=&building=<uuid>&page=0`:

- Роль только из активного серверного контекста, ограничение workforce-ролями.
- Проверяет модуль и permission, organization/building/unit, персональное назначение для техника/подрядчика.
- Возвращает rows, total, stats, buildings, pageSize=24, serverTime.
- Запросы read model выполняются в read-only repeatable-read транзакции; параметризованный SQL.
- Завершённые записи сортируются после активных.

Переиспользованы `/api/requests/:id`, `/transition`, `/technicians`, `/messages`, `/photos`; `/api/defects/:id`, `/transition`, `/photos`; `/api/passes/validate`, `/api/passes/:id/events`, `/api/access-events`, `/api/incidents`, общие auth/community/documents/properties/people API.

**Миграций нет.** Новых бизнес-сущностей, ролей и прав не создано.

Существующий lifecycle работы: `new → assigned → in_progress → review → resident_review → closed`; возврат из review/resident_review в in_progress. Дефект: `assigned → in_progress → review → accepted`, возврат из review в in_progress. Это текущие серверные схемы, не полный расширенный lifecycle из ТЗ.

## Запуск

Обычный запуск проекта: `npm run dev:all` (Vite 5173, API 3001). Требуются существующие PostgreSQL, `.env` и миграции по README. Не перезаписывать текущую БД.

На текущем компьютере для отдельного preview: `node scripts/hayat-dev.cjs`. Web: **http://localhost:5176**, API: 3012. Затем `/login` и отдельный аккаунт manager / dispatcher / technician / contractor / security из **`.local/demo-accounts.md`**. Пароли не включаются в отчёт.

Браузерная проверка: `node scripts/hayat-qa.cjs`. По умолчанию использует установленный Windows Chrome и bundled Playwright; пути можно переопределить `CHROME_PATH`, `PLAYWRIGHT_PATH`, `HAYAT_ORIGIN`.

API: `npm run test:api` — отдельная `vernatun_test`, сохраняет рабочую БД.

Новые внешние сервисы и npm-зависимости не добавлены. Публикация в интернет и магазины не выполнялась.
