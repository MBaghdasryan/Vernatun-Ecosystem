Продолжи существующую email-интеграцию Vernatun.

Текущая архитектура EmailProvider уже реализована:

- ResendEmailProvider
- SMTPEmailProvider
- DevelopmentOutboxProvider

НЕ переписывай EmailProvider и не привязывай invitation/reset/delegation business logic напрямую к Resend.

Задача этого этапа — добавить production-grade обработку **Resend Webhooks**, чтобы Vernatun мог отслеживать реальный lifecycle отправленных email.

# 1. ЦЕЛЬ

После отправки письма Vernatun должен различать:

- provider accepted message;
- sent;
- delivered;
- delayed;
- bounced;
- complained;
- failed.

Не считать `resend_accepted` подтверждением доставки.

---

# 2. ENDPOINT

Добавить публичный HTTPS endpoint:

`POST /api/webhooks/resend`

или, если существующие conventions требуют другого пути:

`POST /api/integrations/resend/webhook`

Выбрать один канонический путь и добавить его в OpenAPI.

Endpoint:

- не требует пользовательской session auth;
- НЕ должен быть открыт без webhook signature verification;
- принимает только POST;
- имеет body-size limit;
- возвращает быстрый 2xx после безопасной обработки.

---

# 3. SIGNATURE VERIFICATION — ОБЯЗАТЕЛЬНО

Resend webhooks используют подписанные webhook requests.

НЕ доверять JSON payload до проверки подписи.

Использовать официальный SDK / webhook verification mechanism, совместимый с текущей интеграцией Resend.

Секрет webhook хранить только server-side.

Предпочтительное имя:

`RESEND_WEBHOOK_SECRET`

Если Replit Connector предоставляет signing secret другим безопасным способом, использовать его, но не выводить secret в код, UI, лог или audit.

При invalid signature:

- вернуть 400/401 согласно выбранному contract;
- ничего не записывать как успешное событие;
- создать безопасный security log;
- не логировать signing secret.

---

# 4. RAW BODY

Проверь требования Resend/Svix signature verification.

Если verification требует исходный raw request body:

не JSON.stringify повторно распарсенный объект.

Сохрани raw body в middleware только для этого endpoint или безопасным централизованным способом.

Не ломай остальные Express JSON routes.

---

На первом этапе обрабатывать минимум:

- `email.delivered`

Не включать tracking logic в security decisions.

# 8. STATUS MODEL

- `sent`
- `delayed`
- `delivered`

- `complained`
- `failed`

---

# 9. STATUS PRECEDENCE

Webhook events могут прийти:

- с задержкой;
- повторно;
- не обязательно в ожидаемом порядке.

Поэтому нельзя слепо записывать status последним event.

Создать deterministic state policy.

Например:

`accepted`
→ `sent`
→ `delayed`
→ `delivered`

Terminal negative statuses:

- bounced
- complained
- failed

Но внимательно проверить semantics Resend.

Не разрешать старому `email.sent` откатить уже `delivered`.

Сохранять ВСЕ events отдельно, а aggregate status вычислять/обновлять безопасно.

---

# 10. IDEMPOTENCY

Resend может повторно доставлять webhook.

Повтор одного provider event:

- не создаёт duplicate event;
- не вызывает повторную business action;
- возвращает success после определения duplicate.

---

# 11. MATCHING MESSAGE

После email send существующий ResendEmailProvider получает provider message ID.

Убедиться, что message ID сохраняется в Vernatun.

Webhook должен находить email по:

`provider = resend`
+
`provider_message_id = data.email_id`

Не пытаться матчить письмо только по email адресату или subject.

# 14. PASSWORD RESET

Очень важно.

Webhook delivery status password-reset письма — только observability.

Нельзя:

- возвращать reset token;
- раскрывать наличие пользователя;
- автоматически повторять reset без нового controlled flow.

Если reset email bounced:

зафиксировать delivery failure безопасно.

Public forgot-password response всё равно остаётся нейтральным.

---

# 15. COMPLAINT

При `email.complained`:

- отметить email delivery;
- создать warning в Platform Operations / Email health;
- не блокировать автоматически весь пользовательский account.

Если позже появится marketing/broadcast subsystem, complaint может влиять на marketing suppression отдельно.

Transactional security email policy не смешивать с маркетинговой подпиской.

---

# 16. BOUNCE

Для bounce сохранить безопасные provider details, например:

- type;
- subtype;
- safe reason/message

если они присутствуют в официальном payload.

Не хранить лишнюю чувствительную информацию.

Можно добавить `email_address_health` foundation:

- recipient
- last_bounce_at
- bounce_type
- complaint_at

Но НЕ запрещать навсегда transactional email после одного temporary bounce без policy.

# 39. ФИНАЛЬНЫЙ РЕЗУЛЬТАТ

После реализации email pipeline Vernatun должен выглядеть так:

Invitation / Reset / Notification
        ↓
EmailProvider
        ↓
Resend
        ↓
resend_accepted
        ↓
email.sent webhook
        ↓
email.delivered
          OR
email.delivery_delayed
          OR
email.bounced
          OR
email.complained
          OR
email.failed
        ↓
Vernatun Email Delivery Store
        ↓
Console / Operations / Support visibility

Главный принцип:

**Provider acceptance, transport, and mailbox delivery are different states and must never be conflated.**

Начни с аудита уже существующей email delivery модели и расширь её без переписывания работающего EmailProvider.
