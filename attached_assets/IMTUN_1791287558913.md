# ImTun: реализация и границы готовности

Дата: 30 сентября 2026.

**REAL:** адаптивный веб-кабинет жильца на общей платформе Vernatun.
**PARTIAL:** полный объём продуктового задания. Нативные приложения, платёжный провайдер и premium store builds не реализованы. Это не готовый релиз в App Store / Google Play.

## A–D. Аудит, повторное использование и изменения

До работы существовали React 19 / Vite / TypeScript, Express / PostgreSQL, Passport, httpOnly session cookies, CSRF, scoped role assignments, модули организации, три языка и три валюты. Существовали `/imtun/owner`, `/imtun/renter`, `/imtun/family`, но они использовали общий административный интерфейс.

Повторно использованы общий вход/восстановление/приглашения/TOTP, контексты, API-клиент, существующие таблицы и операции заявок/WorkOrder, финансов, документов, счётчиков, объявлений, голосований, пропусков, аренды и делегирования. Второй базы пользователей и копий бизнес-сущностей нет.

Новая оболочка `src/imtun/ResidentApp.tsx` заменяет общий кабинет только для resident roles. Одна главная собирается по permissions + modules. Добавлены приветствие, серверный финансовый итог, быстрые действия, активные заявки, объявления, собрания, договор арендатора, срок доступа, профиль, адаптивная боковая/нижняя навигация, сетевой статус и повторная загрузка. Внутренние экраны используют существующие рабочие формы и серверные операции.

`server/access.ts` теперь возвращает проверенные `building_name` и `unit_number` в контекстах. Выбор контекста показывает квартиру и дом. Уведомления получили ссылки на защищённую страницу заявки.

Использованы референсы №2 (собственник) и №3 (арендатор). №1 — логотип: SHA-256 существующего ассета совпадает с предоставленным файлом. №4–6 относятся к сотрудникам. Референс семейного экрана среди вложений отсутствует; семейный экран построен из общей архитектуры с меньшим набором действий.

## E. Маршруты

- `/login` — общий вход Vernatun.
- `/imtun/owner`, `/imtun/renter`, `/imtun/family` — главная соответствующего назначенного контекста.
- `/imtun/payments` — начисления, детали, подтверждённые платежи и корректировки.
- `/imtun/requests?requestId=<uuid>` — заявки, переписка, фото, история и подтверждение результата.
- `/imtun/meters`, `/imtun/announcements`, `/imtun/documents`.
- `/imtun/access`, `/imtun/meetings`, `/imtun/delegations`, `/imtun/leases`.
- `/imtun/notifications`, `/imtun/settings` — уведомления и профиль/безопасность.

Недоступный раздел не монтируется, прямые API-запросы проверяются сервером.

## F–G. API и миграции

Новых endpoints нет. Расширен ответ существующего `/api/auth/session` (метки контекстов).

Главная: `/api/units`, `/api/role-insights?currency=…`, `/api/requests`, `/api/announcements`, `/api/meetings`.

Общие операции: `/api/auth/context`, `/api/auth/preferences`, `/api/auth/logout`; `/api/invoices`, `/api/finance/invoices/:id/details`; `/api/requests/:id`, `/transition`, `/messages`, `/photos`; `/api/meters/:id/readings`; `/api/passes` и действия существующего lifecycle; `/api/delegations`; `/api/documents` и защищённые downloads; `/api/leases`; `/api/agenda/:id/vote`; `/api/notifications/:id/read`; существующие MFA endpoints.

Миграции для изменений не нужны. Рабочая БД не сбрасывалась и не пересоздавалась. Тестовые назначения создаются и удаляются только в `vernatun_test`.

## H. Права

Источник полномочий — текущий server-resolved context: пользователь, организация, дом, квартира, назначение и срок. После смены контекста оболочка перемонтируется; старые карточки не переносятся. Сервер сохраняет существующие проверки действующего назначения, членства и модулей.

- Финансы фильтруются по `payer_user_id`; у арендатора нет автоматического доступа к долгам собственника.
- Семья не получает финансы, голосование или управление семьёй по умолчанию.
- Заявки, документы, уведомления, пропуска и голоса проверяются существующими серверными scopes.
- Права не зависят от цвета или логотипа.
- Секреты аутентификации не добавляются в localStorage.

## I–J. Branding и build profiles

**REAL:** общий логотип, дизайн-токены, централизованный `BrandConfig`, проверка hex-цвета организации и runtime-тема.

**PARTIAL:** `AppBuildProfile` описывает development/staging/production, bundle/package identity, logo/icon/splash, store metadata, domains и ссылку на push configuration. Это подготовка контракта, не мобильный сборщик. Конфигурация контактов/URL предусмотрена, незаданные контакты не выдумываются. Полного UI управления branding и runtime-конфигурации всех полей через API пока нет.

**NOT IMPLEMENTED:** native iOS/Android targets, подписанные сборки, premium branded store binary, biometric unlock, store publishing. Иконка для нативного приложения пока не подготовлена; текущий профиль ссылается на существующий favicon.

## L–N. Что осталось и ограничения

**MOCK / DEMO:** существующие аккаунты и контент seed. Новые домашние карточки не содержат фиктивных сумм, объявлений или дат; всё приходит из API. Текст бизнес-записей на армянском не переводится автоматически при выборе русского интерфейса.

**PARTIAL:** запросы поддерживают исходные поля subject/description, фото, сообщения и lifecycle. Отдельные category/subcategory, preference contact и согласование/перенос визита требуют развития API. Показана настоящая дата создания, без выдуманной записи мастера.

**PARTIAL:** уведомления используют существующую инфраструктуру заявок. Остальные типы уведомлений, полноценные cross-context deep links и push пока отсутствуют. Ссылка заявки повторно проверяет доступ на сервере в текущем контексте.

**PARTIAL:** объявления и встречи ограничены возможностями существующего backend; расширенное таргетирование на этаж/подъезд, полный правовой процесс голосования и расширенные материалы собраний не добавлены.

**PARTIAL:** семья использует существующее делегирование, а не новый полный invitation/acceptance workflow. Дополнительная повторная аутентификация чувствительных действий не добавлялась.

**PARTIAL:** аналитика — отключённый адаптер без персональных payload, базовые события открытия разделов. Полный набор событий не подключён.

**NOT IMPLEMENTED / external:** онлайн-эквайринг и server/provider verification, выдача новых квитанций провайдером, SMS/email delivery, push, контроллеры дверей, PWA service worker/offline cache, native secure storage/биометрия. Кнопка «Способы оплаты» ведёт к начислениям; экран деталей честно сообщает об отсутствии провайдера. Нет ложного успешного платежа или открытия двери.

Контекст хранится в общей серверной сессии: несколько вкладок используют один активный контекст. Это исходная архитектура; полноценную независимость контекстов вкладок нужно проектировать отдельно.

## O. Запуск и просмотр

Для уже настроенного проекта с работающей PostgreSQL:

```sh
node scripts/imtun-dev.cjs
```

Открыть `http://localhost:5175/login`. API использует порт 3011, чтобы не занимать 3001 другого проекта. Войти `unit.owner@vernatun.test`, `renter@vernatun.test` или `family@vernatun.test`. Индивидуальные пароли находятся только в `.local/demo-accounts.md`.

Обычный запуск сохранён:

```sh
npm run dev:all
```

Он использует порты 5173/3001. Можно задать `VERNATUN_API_ORIGIN` для Vite proxy. Подготовка чистой среды и PostgreSQL описана в основном README; не запускайте seed с production-секретами.

```sh
npm run typecheck
npm run test:api
npm run build
node scripts/imtun-qa.cjs
```

Для браузерных тестов задать `PLAYWRIGHT_PATH`, `CHROME_PATH`, `IMTUN_ORIGIN`, если окружение отличается от этой Windows-машины. Скрипт использует приватные локальные demo credentials, не выводит их и не включает их в отчёт.
