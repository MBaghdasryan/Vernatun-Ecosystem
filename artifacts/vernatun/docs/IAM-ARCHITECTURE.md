# Vernatun IAM — архитектура завершения интерфейсов

Дата: 2026-10-07. Статус: **проект решения после исходного аудита; новый IAM ещё не реализован**.

Спецификация: `attached_assets/Pasted-Continue-development-of-the-existing-Vernatun-project-T_1791356633425.txt`.
Этот документ не является подтверждением применённых миграций или браузерной приёмки.

## 1. Что сохраняем

- React/Vite, Express, PostgreSQL, Passport/session и существующий RBAC.
- 14 неизменяемых системных шаблонов из `server/roles.ts`.
- Существующие `users`, `role_assignments`, приглашения, организации, здания, помещения.
- Разделение Console, OS, HAYAT, ImTun; переключение продукта не даёт дополнительных прав.
- Общие `contexts`, `context`, `requirePermission`, `scopedUnit`; не создаём параллельный механизм разрешений.
- Ограничения подписки, модулей, временного доступа поддержки, аренды и семейного делегирования.
- Все финансовые, сервисные и документные движки остаются прежними.

## 3. Целевая модель — добавочная, не заменяющая

### 3.1 Системная роль и пользовательский профиль

Системная роль остаётся первичным типом контекста и определяет продукт, роль в workflow
и специальные ограничения. Пользовательский профиль задаёт допустимый набор возможностей
внутри этого типа контекста. Профиль не должен превращать подрядчика в бухгалтера,
семью в собственника или поддержку в администратора организации.

Нельзя просто записать новое строковое имя в `role_key`: код бизнес-правил уже использует
стандартные role keys. Нельзя без анализа объединять права нескольких назначений.

Предлагаемые сущности, подлежащие проверке при реализации:

- глобальный шаблон пользовательского профиля с признаком tenant-allowed;
- профиль организации: имя, описание, базовый системный тип, версия, статус,
  разрешения, допустимые виды scope, допустимые модули, автор;
- ссылка действующего назначения на профиль;
- ограничение разрешения назначения: permission, reason, actor, период действия;
- независимые account status и assignment status.

Для нескольких зданий сначала проверить возможность безопасно использовать несколько
существующих назначений. Новую `assignment_scopes` создавать только если текущая модель
не покрывает требуемую редактируемую группу scope. Нельзя заменить один scoped-контекст
неограниченным organization-контекстом ради удобства интерфейса.

### 3.2 Право делегирования — не копия собственных рабочих прав

Администратор организации уже может назначить бухгалтера, не имея права публиковать
начисления лично. Поэтому правило «разрешать только права, которые есть у самого
администратора» не отражает текущую модель.

Нужен отдельный явный allowlist делегирования по типу профиля и домену.
Наличие `roles.assign` само по себе не должно разрешать любые произвольные permission keys.
Неизвестные разрешения, platform-only права и несовместимые комбинации отклоняются сервером.
Связанные permissions проверяются: например, выполнение операции требует подходящего
чтения и scope. Список зависимостей необходимо привязать к реальным серверным операциям.

### 3.3 Персональные ограничения и исключения

Первый безопасный вариант — **только ограничивающие overrides**, привязанные к назначению.
Явный deny имеет приоритет над наследуемым allow. Не распространять ограничение
одной организации на другие назначения пользователя.

Исключительное расширение прав — отдельная операция с отдельным allowlist и полномочием,
причиной, автором, аудитом и, где нужно, сроком. Не реализовывать как свободную галочку.
Пока механизм не реализован и не проверен, UI не предлагает такое расширение.

## 4. Единое вычисление доступа

Последовательность:

1. Аккаунт существует и допускает вход/действие.
2. Сессия действительна; при необходимости подтверждены MFA и свежая аутентификация.
3. Назначение активно по статусу и времени.
4. Организация действительна; соблюдены специальные правила support/lease/delegation.
5. Системный тип и пользовательский профиль допускают permission.
6. Нет действующего персонального deny.
7. Организация имеет нужный модуль и entitlement.
8. Подписка допускает чтение/изменение с учётом существующих явных исключений.
9. Конкретный объект принадлежит допустимой организации/зданию/помещению.
10. Применены бизнес-условия: payer, assignee, ownership, независимая приёмка, версия, статус.

Это схема реализации, а не утверждение, что все десять слоёв уже существуют в виде
единого нового policy engine. Новый resolver следует встроить в текущие guards.

`Check access` должен использовать тот же evaluator, что и endpoint, иначе объяснение
может обещать доступ, который действие отвергнет. Проверка без objectId сообщает
«право допускается, область объекта ещё не проверена», а не безусловное ALLOWED.

## 5. Административные границы

### Console

Предлагаемые маршруты: `/console/users`, `/console/roles`, `/console/permissions`.

Platform admin видит административные метаданные аккаунта, назначения, MFA state,
безопасные метаданные сессий и аудит, но не получает финансовые записи арендаторов.
Нельзя выдавать session tokens, MFA secrets, password hashes или reset tokens.

Защитить последнего действующего platform admin, самоотключение и конкурентные изменения.
Операции блокировки/деактивации и reset requirement должны прекращать действия старых сессий.
Проверка только на странице login недостаточна.

Создание управляемого аккаунта не означает вывод временного пароля. Предпочтительный
путь — приглашение/активация с существующим безопасным email flow.

### Vernatun OS

`/os/people` — сотрудники и назначения; `/os/roles` — профили; карточка сотрудника
с вкладками Overview, Assignments, Roles, Permissions, Scope, Activity.

Глобальные Sessions/MFA доступны только в явно разрешённом административном объёме:
tenant admin не получает управление сессиями сотрудника в других организациях.
Отзыв назначения не удаляет аккаунт, его документы, финансовые записи или историю.

## 6. Контракты и конкурентность

- Поиск/таблицы — server-side paging, ограничения размера, стабильная сортировка.
- Все mutation body — strict validation; actor/organization берутся из проверенного контекста.
- Обновления профиля/назначения — version/CAS; устаревший редактор получает конфликт.
- Изменение разрешений немедленно учитывается сервером, не только после logout.
- В UI смена контекста очищает данные и игнорирует поздние ответы.
- Structured audit: actor, target, organization, action, reason, before, after, timestamp.
- Не включать секреты и токены в before/after.

## 7. Проверка миграций

Только добавочные миграции после изолированной проверки. До применения:

1. Снимок структуры, количества и контрольных сумм исходных бизнес-данных.
2. Прогон старой схемы → новая схема в отдельной базе.
3. Проверка сохранения всех старых назначений и стандартных ролей.
4. Негативные API-тесты tenant isolation, module/subscription, scope, revoked/disabled.
5. Проверка неизменности исходных бизнес-данных и private-file references.

Не запускать seed/reset на основной базе и не выполнять QA на реальных пользователях.

## 8. Обязательная приёмка IAM

| Сценарий | Ожидаемый результат | Текущий статус нового IAM |
|---|---|---|
| Org admin редактирует platform assignment | Отказ | Не проверен |
| Org admin присваивает неделегируемое право | Отказ | Не реализовано |
| Профиль другой организации | Отказ | Не реализовано |
| Профиль пытается включить выключенный модуль | Отказ | Не реализовано |
| Subscription read-only + mutation | Отказ, кроме прежних явных исключений | Новый профиль не проверен |
| Restriction снимает наследуемое право | Отказ немедленно | Не реализовано |
| Назначение Building A запрашивает Building B | Отказ | Новый редактор scope не проверен |
| Account disabled с несколькими сессиями | Все действия прекращаются | Новый lifecycle не реализован |
| Assignment suspended при другом активном назначении | Прекращается только соответствующий доступ | Не реализовано |
| Platform IAM → tenant invoices | Не даёт доступа | Новый IAM не проверен |
| Два редактора меняют одну роль | CAS conflict, без потери изменения | Не реализовано |
| Debugger и endpoint | Совпадающий результат для того же объекта | Не реализовано |
