# Handoff: отдельное Android-приложение HAYAT для подрядчиков

Скопируйте это задание в отдельный Replit-проект, в котором будет создан мобильный Expo artifact HAYAT. Этот проект предназначен для самостоятельного HAYAT APK; не объединяйте его с ImTun.

## Цель

Создать демонстрационное Android-приложение **HAYAT by Vernatun** для пользователя с активным серверным контекстом подрядчика. Приложение должно подключаться к существующему Vernatun API и показывать реальные назначенные этому подрядчику дефекты. Подрядчик должен иметь возможность открыть дефект, начать работу, добавить фотоотчёт/комментарий и отправить результат на проверку.

Это мобильный клиент существующего API, а не новый backend. Не создавать отдельную базу, пользователей, роли, права или бизнес-логику в приложении. Сервер Vernatun остаётся единственным источником авторизации, назначения дефекта и допустимых переходов.

## Подключение к API

API host: `https://api.vernatun.io`. В целевом проекте настройте несекретную shared environment variable:

```text
EXPO_PUBLIC_DOMAIN=api.vernatun.io
```

Полный API prefix: `https://api.vernatun.io/api`. Не записывать host многократно в экранах; использовать общий типизированный API client. При наличии исходного generated client/OpenAPI — использовать его или сгенерировать клиент из контракта, не переписывая типы вручную по экранам.

Основные уже существующие маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/auth/session` | Проверить сессию и получить CSRF token |
| POST | `/api/auth/login` | Вход по email/password; поле `code` передавать только если сервер запросил MFA |
| POST | `/api/auth/context` | Выбрать уже разрешённый сервером контекст: `{ "id": "<context UUID>" }` |
| POST | `/api/auth/logout` | Завершить серверную сессию |
| GET | `/api/hayat/queue` | Серверная очередь HAYAT; для contractor возвращает только назначенные ему дефекты |
| GET | `/api/defects/{id}` | Получить разрешённые детали конкретного дефекта |
| GET | `/api/defects/{id}/collaboration` | Получить разрешённую историю сообщений, фото и отчётов |
| POST | `/api/defects/{id}/messages` | Добавить уточняющее сообщение; тело `{ "key": "<UUID>", "body": "..." }` |
| POST | `/api/defects/{id}/transition` | Начать работу или передать результат на проверку |
| POST | `/api/defects/{id}/photos` | Загрузить фото как raw binary |
| GET | `/api/defect-photos/{id}` | Получить фото с повторной серверной проверкой доступа |

### Очередь подрядчика

`GET /api/hayat/queue` поддерживает параметры `search`, `status`, `building` и `page`. Сервер возвращает `rows`, `total`, статистику статусов, доступные здания, `pageSize` и `serverTime`; размер страницы сейчас равен 24. Использовать серверные фильтры/страницы, не загружать все дефекты организации и не фильтровать назначение только на устройстве.

Для роли contractor API выбирает записи `defects`, где `contractor_id` совпадает с текущим вошедшим пользователем; одновременно применяются организация, building/unit scope, модуль и permission. Не подменять этот источник заявками жителей или нарядами техников. Дефект может иметь `work_order_id: null` — это ожидаемо для текущей модели.

Карточка очереди может показывать только фактически полученные поля: тема, описание, статус, здание, квартира/номер помещения, location и due date, если они есть. Для деталей, фото, отчётов и истории загружать разрешённый detail/collaboration endpoint. Если поле отсутствует, показывать нейтральное состояние, не придумывать данные.

### Переходы дефекта и действия

Использовать `version` из свежего ответа API и отправлять уникальный UUID `key` для каждой изменяющей операции:

```json
{ "key": "<UUID>", "action": "start", "version": 1, "note": "" }
```

```json
{ "key": "<UUID>", "action": "report", "version": 2, "note": "Описание выполненной работы" }
```

Для подрядчика допустимы только:

- `assigned` → действие `start` → `in_progress`;
- `in_progress` → действие `report` → `review`; отчёт должен содержать не менее 5 символов.

Отчёт ограничен сервером 4000 символами. Успех показывать только после подтверждения API. После `409` (устаревшая версия или недопустимый переход) перечитать серверное состояние и объяснить пользователю конфликт; не отправлять автоматически старое изменение с новой версией. Не предлагать подрядчику `accept`, `return` или `reopen`: это не его полномочия. Принятие и возврат результата выполняет уполномоченный менеджер.

Сообщение в collaboration — отдельное действие, оно не меняет статус. Повтор при сетевой неопределённости должен использовать тот же operation key и то же тело, а не создавать дублирующую операцию.

### Фото

- Загружать только через `/api/defects/{id}/photos` с `Content-Type: application/octet-stream`, текущей сессией и CSRF header.
- Сервер принимает до 6 MiB и сам проверяет/санитизирует JPEG, PNG или WebP в приватное JPEG-хранилище. Клиентское сжатие допустимо для удобства, но не заменяет серверную проверку.
- Не загружать файлы напрямую в object storage, не создавать публичные URL, не кэшировать приватные фото в общей галерее.
- Для отображения использовать `/api/defect-photos/{id}` и обработать 403/404 как отсутствие текущего доступа.

## Сессия, права и безопасность

- Получать cookie-сессию через API и передавать cookie при запросах; для каждого unsafe request (`POST`) передавать актуальный `X-CSRF-Token`. Вызов `/auth/session` должен инициализировать/обновлять CSRF-состояние.
- Проверить на реальном Android, что cookie сохраняется между запросами и работает после перезапуска приложения. Не складывать пароль или session cookie в AsyncStorage, логи, аналитические события или исходный код.
- Контексты и разрешения брать только из ответа API. Войти можно только в server-returned context с `role_key === "contractor"` и разрешённым HAYAT-продуктом/назначением. Если такой контекст отсутствует, показать понятное сообщение «Нет активного доступа подрядчика» и обратиться к менеджеру.
- Не разрешать выбрать в UI manager, dispatcher, technician, security, resident или org admin. Не выдавать права по факту наличия экрана.
- Сервер — окончательная проверка каждого чтения и действия. Ошибки 401/403/404/409 должны оставаться ошибками; не подменять их cached payload или фиктивным успехом.
- При logout/смене контекста очистить чувствительные query cache и выбранный дефект. Не показывать данные другого пользователя/организации после повторного входа.
- Тестировать запись только на специально выделенной тестовой учётной записи и тестовом дефекте. Не выполнять пробные переходы/загрузки на production-записях заказчиков без отдельного разрешения.

## Экраны MVP

1. **Запуск и восстановление сессии** — загрузка, понятная ошибка сети и кнопка повторить.
2. **Вход** — email/password, серверные ошибки, optional MFA code только по ответу API. Не хранить credentials.
3. **Контекст** — если сервер вернул несколько допустимых contractor-контекстов, дать выбрать один; иначе открыть единственный. Контекст выбирается через API.
4. **Мои работы** — только assigned defects подрядчика; краткие счётчики по статусам, поиск и фильтр статуса, ручное обновление, серверная пагинация.
5. **Детали дефекта** — тема, описание, адрес/здание/номер квартиры, location, срок если есть, текущий статус, фото, история/отчёты и доступные сообщения.
6. **Выполнение** — крупная кнопка «Начать работу» только для `assigned`; после подтверждения показать состояние `in_progress`.
7. **Отчёт** — текст не короче 5 символов, добавление фото, подтверждение перед отправкой; после успешного ответа статус `review`, экран становится read-only для действий подрядчика до серверного обновления.
8. **Профиль/выход** — пользователь, выбранная организация/контекст и безопасный logout.

Обязательно сделать loading, empty, offline, retry, validation и server-error состояния. Не использовать mock records как будто это production. Если API недоступен или список пустой, показать настоящее пустое/ошибочное состояние.

## Offline и фоновые действия

Для первой версии достаточно понятного offline-индикатора, ручного повторного чтения и блокировки изменяющих действий без сети. Не отправлять отчёты или фото автоматически в фоне после восстановления соединения. Если разработчик добавит локальные черновики, привязать их к user + context + defect ID; синхронизацию запускать только по явному действию пользователя и после свежей серверной авторизации. Logout не должен незаметно восстанавливать offline identity.

Push, realtime, открытие дверей, новые роли, изменение дефектов вне назначений и новые backend/schema migrations не входят в этот MVP. Не показывать неподключённые возможности как работающие.

## Проверка готовности

Перед передачей клиенту:

1. TypeScript typecheck и Expo production/prebuild validation проходят без отключения проверок.
2. Expo Go запускается с QR; Android layout проверен на узком экране и на реальном устройстве либо эмуляторе.
3. Вход contractor и сохранение cookie-сессии проверены на Android; необязательный web preview не считается заменой native-проверке.
4. Очередь содержит назначенные текущему подрядчику записи; другой подрядчик и другая организация не видны.
5. `start` и `report` меняют состояние только после ответа API; отчёт короче 5 символов блокируется и сервер всё равно остаётся авторитетным.
6. Фото загружается через защищённый backend-маршрут; прямых public/object-storage URL нет.
7. Проверены 401, 403, 404, 409, пустая очередь, отсутствие сети, logout и повторный вход без утечки предыдущего контекста.
8. В финальном отчёте перечислить файлы, проверенные команды/устройства, реально проверенные API-сценарии и оставшиеся ограничения. Не утверждать APK-build или live API acceptance, если они фактически не выполнялись.
