# Vernatun Cloud ↔ Edge: аудит перед интеграцией

Статус: **контракт установленного Edge Agent не подтверждён**. Этот аудит не
означает, что регистрация, сокет или физические команды уже работают.

## Подтверждено по текущему репозиторию

- Активный API: `artifacts/api-server/archive/vernatun/server/`; Express-роутеры
  монтируются в `app.ts` под `/api`. `/api/health` уже существует. Код
  API должен сохранять нынешние session/CSRF/CORS и внешний API v1.
- Активный веб-интерфейс: `artifacts/vernatun/src/`; существующие Console,
  OS, HAYAT и ImTun используют маршруты и роль/контекст из общего продукта.
  Мобильный ImTun находится в `artifacts/imtun-mobile/`.
- Идентичность пользователей: `access.ts`, `roles.ts`,
  `iam-evaluator.ts`, `iam-resource.ts`; существующие users,
  role_assignments, memberships, organizations, buildings, units,
  resident_delegations и support_access_grants. Действующие права нельзя
  заменять одним сравнением role key.
- Действующие аудиторские и модульные политики, lifecycle жителя и
  уведомления надо переиспользовать. Аутентификация машины не является
  человеческой сессией и не должна принимать присланные клиентом права.
- Миграции версионируются SQL-файлами в `server/migrations/`;
  последняя в дереве на момент аудита — `039_payment_foundation.sql`.
  Новые объекты следует добавлять отдельной миграцией после проверки ledger.
- В рабочем дереве нет Edge Agent, Command Authorization Layer или
  ThingsBoard-интеграции. В Cloud пока нет `edge_nodes`, Edge machine auth
  или `/api/edge/v1/*`. Описание испытаний локального стенда находится
  только в приложенном master prompt.

## Принципиальные границы

- Edge инициирует исходящее соединение; Cloud не соединяется с LAN/ThingsBoard.
- `FIRE.CONTROL` и `ELEVATOR.SAFETY_CONTROL` всегда запрещены.
  Не испытанные Door/HVAC/Pump/Water команды не включаются автоматически.
- Нельзя помечать открытие шлагбаума успешным до подтверждённого ответа
  адресного Edge; просроченное OPEN нельзя повторять после реконнекта.
- Токены/bootstrap/credential передаются через защищённый путь; ни один
  токен или сырой ответ устройства не записывается в обычный аудит.

## Что требуется сверить с *установленным* Edge Agent до подключения

1. Фактические body/header форматы `register`, WebSocket `connect` и
   `EDGE_HELLO`; где и как агент хранит bootstrap и постоянный credential.
2. Версия и структура inventory, heartbeat, telemetry, events, alarms и
   command/result; существующий HTTPS fallback и правила повтора.
3. Способ запуска/перезапуска и конфигурация Cloud URL у агента.
4. Как `uk_001` и `building01` сопоставляются с UUID организации/здания
   в текущей базе Cloud; не доверять этим строкам как разрешению доступа.
5. Как Cloud-авторизация транслируется в поля, ожидаемые локальным
   Authorization Layer для Barrier-01, без предоставления лишних прав.

Не следует публиковать маршрут, который принимает bootstrap token и
выдаёт permanent credential, пока его протокол не согласован с уже
установленным агентом. Иначе можно создать неработающий или небезопасный
путь доступа к физическому устройству.
