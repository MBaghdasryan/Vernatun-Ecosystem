# Конфигурация Edge

## Настройки Cloud

| Поле | Диапазон / значение |
|---|---|
| heartbeatSeconds | 10–300 секунд, по умолчанию 30 |
| inventorySeconds | 30–86400 секунд, по умолчанию 300 |
| telemetrySeconds | 5–3600 секунд, по умолчанию 30 |
| enabledModules | `access`, `fire_monitoring`, `elevator_monitoring`, `metering`, `cameras`, `hvac`, `pumps` |
| projectName | Явно введённое название, до 120 символов |
| environment | `unknown`, `test`, `staging`, `production`; только метаданные |
| description | До 2000 символов |

Изменения сохраняются транзакционно с увеличением версии конфигурации и аудитом. Polling не должен заменять несохранённый ввод оператора. Поля запроса строго проверяются; произвольные capability-поля отвергаются.

Конфигурация предоставляется через существующие versioned machine config endpoints. Сохранение в Cloud **не является подтверждением применения на физическом Agent**. Нет выдуманного applied/ack-состояния; динамическое применение, период повторного чтения и поведение конкретной сборки Agent требуют отдельной реальной приёмки.

## Статусы и наблюдения

Текущие серверные пороги:

- Ожидаемый heartbeat: 30 секунд.
- Offline: heartbeat старше 120 секунд либо отсутствующий действующий socket/credential у ранее наблюдаемого узла.
- Устаревший inventory: 600 секунд.
- Устаревшая telemetry: 300 секунд.
- Предупреждение по очереди: от 100 сообщений; критический порог в конфигурации политики — 1000.

Это базовые эксплуатационные значения политики, а не SLA и не измерения сетевого ping. При длинных заданных интервалах пороги увеличиваются: offline не раньше трёх интервалов heartbeat, stale inventory — двух интервалов, stale telemetry — трёх. Диагностика и нормализованный статус используют одну политику.

`ONLINE` требует регистрации, свежего heartbeat, открытого локально известного WebSocket и действующего credential. `DEGRADED` учитывает очередь, локальную авторизацию и устаревшие известные потоки. Отсутствие первого heartbeat означает `UNKNOWN`, а не успешное подключение. Архив/отключение — `DISABLED`. Ожидающая регистрация отдельно показана как `PENDING_REGISTRATION`.

Диагностика возвращает `OK`, `FAILED` либо `UNKNOWN` по наблюдаемым признакам. Пустой поток без пакета не выдаётся за успешную синхронизацию. Время пакета фиксируется и при пустом допустимом batch.

Socket registry сейчас внутрипроцессный. При нескольких API-репликах наблюдение сокета на другой реплике требует общего presence-механизма/маршрутизации; текущая реализация не заявляет такую готовность.

## Защита и совместимость

- v1 продолжает использовать одно здание и прежние заголовки identity.
- v2 продолжает использовать блок и явный список зданий; первичное здание не выдумывается вместо этого контракта.
- Draft не создаёт машинный credential, online-статус или устройство.
- Машинная регистрация может атомарно завершить подходящий draft, не создавая дубликат.
- Регистрация использует неизменяемые tenant/scope/identity/site/name bindings токена.
- Повторный bootstrap предназначен для ожидающего регистрации draft; для зарегистрированного узла применяется существующий lifecycle credentials.
- Мониторинг пожарной системы/лифта не даёт права физического управления безопасностью.

## Известные границы

Текущая диагностика — Cloud-side observation, **не активный ping Windows-хоста и не команда Barrier-01**. Таблицы устройств и истории ограничены размером ответа; это не бесконечный архивный поиск. Изменять сетевые адреса провайдеров, TLS-ключи, merchant secrets или настройки production DB эта страница не позволяет.
