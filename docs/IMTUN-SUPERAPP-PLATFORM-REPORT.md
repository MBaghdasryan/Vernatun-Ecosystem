# ImTun Resident Super App — отчёт о реализации

Дата: 2026-10-26.

## Вердикт

**Весь мастер-промпт: PARTIAL, не закрыт.**

В существующие приложения добавлен работающий набор новых resident-функций, серверных правил и экранов. Это не заявление о реализации и production-приёмке всех 76 разделов. Исходная проверка каждого раздела до изменений сохранена в [IMTUN-SUPERAPP-GAP-AUDIT.md](IMTUN-SUPERAPP-GAP-AUDIT.md).

Production-база, пользовательские пароли, почтовый транспорт, платёжные подключения и работающий Windows Edge этим изменением не модифицировались. Реальные команды шлагбауму не отправлялись.

## Что добавлено

### Единые серверные правила

- `/api/me/contexts`: реальные доступные пользователю resident-контексты.
- `/api/resident/workspace`: профиль, разрешённая квартира/здание, настройки разделов, доступные функции, готовность интеграций, агрегаты Home.
- `/api/resident/profile`: имя, телефон как контактное поле, язык, тема, предпочтительный канал и настройки видимости. Этот маршрут не подменяет подтверждённый email и не заявляет проверку телефона.
- `/api/resident/records/...`: типизированные новые нефинансовые сущности и их допустимые действия.
- `/api/resident/admin/buildings` и `/api/resident/settings`: настройка разделов здания сотрудником с реальными полномочиями.

Organization/building/unit/author вычисляются сервером. Клиент не назначает себе scope. Сохраняются существующие ограничения роли, модулей, аренды, делегирования, MFA и read-only подписки.

Данные Home по начислениям, остаткам, просрочке и фактическим платежам берутся из существующего ledger. Нет второго финансового движка. Семейной роли без `billing.own` финансовые значения не выдаются. Недоступные значения не заменяются нулём.

Сводка Home расширена: последний собственный платёж по распределениям ledger, непрочитанные сообщения только разрешённых диалогов, опубликованные объявления здания, текущие взвешенные голосования (не будущие/завершённые), действующие собственные гостевые пропуска, настроенные экстренные контакты, услуги, ожидающие обязательные соглашения и приглашения семьи. Выключенный модуль или недоступное право возвращает `null`, а не вымышленный ноль. У лифта, доступа и отключений остаются честные состояния отсутствия данных. Сводка выведена на веб-главную и страницу дома; дата последнего платежа отображается в часовом поясе организации.

### Новые продуктовые сущности

| Раздел | Реализовано | Ограничение |
|---|---|---|
| Автомобили | Создание, изменение с версией, удаление собственных записей | Не выдаёт автоматически право проезда |
| Устройства жителя | Регистрация установки, повторяемая регистрация, отзыв связанной сессии | Push-провайдер не подключён; это не доказательство доставки push |
| Соглашения | Версионирование публикации, принятие конкретной версии, отзыв разрешённого согласия | Обязательное соглашение нельзя отозвать; весь activation/onboarding ещё не зависит от этих записей |
| Контакты дома | Настройка персоналом, отображение жителю | Проверена фактическая передача опубликованного контакта из УК жителю |
| Справочник | Opt-in здания + личная видимость имени/квартиры/телефона | Не является общим публичным справочником; полноценный соседский direct messaging не завершён |
| Услуги | Каталог, цены, запрос подписки, проверка сотрудником, запрос отмены | Нет автоматического списания/начисления или полной записи на разовую услугу |
| Диалоги | Приватные текстовые потоки, ответы сотрудников, защита повторной отправки | Нет полного messenger-набора вложений, реакций, черновиков и напоминаний |
| Обсуждения | Сообщения, поддержка темы, жалобы, закрытие/заморозка/возобновление | Проверенное предложение не становится официальным голосованием; перевод в заявку/повестку не завершён |
| Недвижимость | Черновик собственника, публикация через модерацию, избранное, жалоба, приватный запрос | Нет полного фотоальбома, карты, сравнения, сохранённых поисков и записи на просмотр |
| Помощь | Контент персонала по языку пользователя | Не заменяет полноценный platform support ticket |
| Обратная связь | Отдельные идеи/улучшения/проблемы | Не смешана с заявками на ремонт и не заявляется новым support-движком |

Валидация полей раздельная для каждого вида сущности. Существующие finance, IAM, заявки, governance, документы и Edge не перенесены в новый универсальный CRUD.

Секции directory/chat/discussions/marketplace/services включаются для конкретного здания отдельно и по умолчанию выключены. Это настройка продукта, а не предоставление прав.

### API-контракты существующих модулей

В OpenAPI описаны и подключены к сгенерированным клиентам уже существующие:

- счётчики с историей и отправка показания;
- объявления;
- разрешённые документы и защищённое скачивание;
- гостевые пропуска: список, создание, отзыв;
- список уведомлений и отметка прочтения;
- собственные начисления;
- существующие приглашения семьи.

Сохранены канонические обработчики. Создание записи гостевого пропуска не объявляется физическим открытием двери или активацией у провайдера.

### Веб-интерфейс

- Для УК: `/os/resident`, пункт «Сервисы жителей» / локализованный аналог.
- Для администратора платформы: `/console/resident`, с выбором реально доступного здания.
- Для жителя: разделы `/imtun/building`, `/imtun/vehicles`, `/imtun/devices`, `/imtun/agreements`, `/imtun/contacts`, `/imtun/directory`, `/imtun/services`, `/imtun/community`, `/imtun/marketplace`, `/imtun/help`, `/imtun/feedback`, `/imtun/preferences`.
- Серверные действия отображаются по фактическому списку доступных действий.
- Общий QueryClientProvider и CSRF сессионного клиента подключены в точке входа приложения.
- Оформление продолжает существующие navy/white/orange стили. Админские формы имеют отдельные scoped-стили; не меняют глобальную верстку всех ролей.
- Глобальный поиск группирует новые разрешённые resident-записи по разделам. Переход включает `recordKind` и `recordId`, загружает именно разрешённую карточку, выделяет её и переводит фокус; работает после reload. Есть возврат к полному списку. Фильтр по ID не обходит scope/opt-in/module/privacy.

### Мобильный ImTun

В существующий Expo-проект добавлены новые разделы и hub «Сервисы». Используются сгенерированные клиенты и текущий authenticated context:

- профиль/приватность, дом, автомобили, установки устройств, соглашения;
- контакты, справочник, услуги, диалоги, обсуждения, недвижимость, помощь, feedback;
- начисления/платежи и готовность провайдера;
- счётчики и отправка показаний;
- объявления и метаданные документов;
- гостевые пропуска с одноразовым показом созданного токена только в памяти экрана;
- собрания и существующее взвешенное голосование;
- уведомления и настройки каналов;
- приглашение семьи и список существующих приглашений.

Наличие экрана и успешная компиляция не доказывают прохождение его полного мобильного сценария. Нативное открытие/сохранение приватного документа не завершено: web-скачивание есть, native показывает явное состояние недоступности. Реальные платежи, голосования, пропуска и отправка приглашений в этой проверке не выполнялись.

## Проверки и доказательства

### Пройдено

1. Общий `corepack pnpm run typecheck`: все workspace-проекты прошли.
2. API production bundle и migration bundle: сборка прошла.
3. Web production build с необходимыми `PORT` и `BASE_PATH`: сборка прошла; остаётся предупреждение о размере существующего основного bundle.
4. Отдельный серверный набор `--resident-superapp-only`: **15/15** в изолированной тестовой схеме:
   - authentication/context и запрет чужого здания;
   - существующий ledger и скрытие финансов у family;
   - профиль без подмены email/actor;
   - изоляция, строгие поля и версии автомобилей;
   - staff-only настройки разделов и контактов;
   - принятие конкретной версии соглашения;
   - цена услуги из реального каталога и запрет self-approval;
   - приватность диалога, идемпотентность сообщения, закрытый поток;
   - owner draft → moderation для недвижимости;
   - регистрация установки и отзыв только связанной сессии;
   - отдельная обратная связь без подмены scope.
   - корректная нумерация GitHub pipeline 047 и resident schema 048;
   - Home без черновиков, будущих/завершённых голосований и выключенных модулей;
   - приватность счётчика сообщений и продвижение отметки прочтения;
   - группировка поиска и точные ссылки без обхода принадлежности записей.
5. Один браузерный resident-сценарий в изолированной схеме:
   - вход org_admin и настройка пяти opt-in секций;
   - создание emergency-контакта;
   - вход owner и подтверждение видимости того же контакта;
   - создание автомобиля, reload, редактирование, сохранение, удаление;
   - сохранение и reload настройки приватности;
   - отсутствие финансовой навигации у family;
   - 360 px: доступность кнопки клавиатурой и отсутствие явного горизонтального обрезания на проверенном экране.
6. Дополнительный узкий браузерный проход после расширения Home/поиска: УК создала emergency-контакт, owner увидел его в Home; Ctrl+K → локализованная группа контактов → точная выделенная карточка; reload сохранил выбор, «Все записи» вернуло полный список. Проверены Home 1440 px и карточка 390 px в изолированной схеме. Реальные платежи, устройства и production не затрагивались.

Первый запуск браузерного сценария обнаружил отсутствие QueryClientProvider. Ошибка исправлена, исходный сценарий повторно пройден. После снимка также исправлены сброс подтверждения сохранения настройки, избыточный размер чекбоксов и локализация известных категорий карточек. Полная повторная визуальная приёмка этих косметических правок не заявляется.

### Не засчитывается как пройденное

- Все экраны всех 14 ролей и все семь старых сквозных цепочек заново не проходились.
- Pixel/parity всех 15 референсов не завершена.
- Полная матрица 360/390/768/1024/1440, screen reader и touch targets не выполнена.
- Физические Android/iPhone и native document-sharing не приняты.
- Мобильное web-preview загружает приложение, но его запрос к production `/api/auth/session` блокируется CORS origin preview. Production CORS не ослаблялся. Необходимо отдельное безопасное dev-подключение/проверка на телефоне.
- Production-приёмка и применение новой схемы в Coolify не выполнялись.

## Что ещё требуется из мастер-промпта

Внешние зависимости:

- Контракты и подтверждённая активация property/utility PSP, saved methods и autopay.
- BLE, домофон, камеры, biometric/elevator adapters и их реальные устройства/политики.
- Push-доставка и подтверждённый AI/vision provider. Не подключённая интеграция отображается как неготовая, а не «успех».

Незавершённые внутренние функции — это **не** внешние блокеры:

- Дополнительные реальные источники Home для отключений/лифта/доступа, расширенные данные объектов и парковок. Текущие разрешённые объявления/голосования/сообщения/пропуска и последний платёж уже включены.
- Проверка телефона/email, изображения профиля и полная привязка activation к обязательным соглашениям.
- Все изменения членов семьи/арендаторов, suspend/restore, payer delegation и их полный mobile UI.
- Соседские direct messages с отдельными правилами privacy; расширенный messenger.
- Resident-safe общедомовая финансовая прозрачность.
- Сценарий разовой услуги с временем/подтверждением и каноническим work order.
- Обсуждение → реальная заявка / управляемая повестка собрания без обхода существующего governance.
- Полный marketplace, включая фото, сравнение, карту, saved searches и просмотр.
- Сохраняемые AI conversations, photo-to-request, отдельные platform support tickets.
- Расширенные настройки каналов/quiet hours и полная проверка языка/темы на всех поверхностях. Точный drill-down новых resident-записей в веб-поиске уже проверен.
- Все оставшиеся требования и доказательства из исходной 76-строчной матрицы.

## Схема и выкладка

Добавлена аддитивная `048_resident_superapp.sql`, без удаления пользовательских данных. Номер 047 сохранён для `047_update_release_pipeline.sql` из GitHub; содержимое этого файла не изменено. В предыдущей локальной версии те же SQL находились под именами `038_update_release_pipeline.sql` и `047_resident_superapp.sql`. Уже применённые файлы нельзя повторно исполнять или произвольно менять их checksum: локальная история согласуется только после точной проверки контрольных сумм. Это не применение к production.

Перед выкладкой в Coolify:

1. Создать и проверить резервную копию, убедиться в целевой базе и версии API.
2. Запустить существующую read-only команду `db:migrate:coolify:plan`.
3. Если есть drift — остановиться и разобраться; не создавать таблицы вручную.
4. Применять только pending-миграции штатной подтверждаемой командой проекта в согласованное окно.
5. Развернуть согласованные API/frontend/mobile версии.
6. Проверить `/api/health`, вход, выбор context и новые resident-экраны.
7. Включать новые разделы только для выбранных зданий, не глобально.

Отдельно существующий Windows Edge / Barrier e2e остаётся на паузе; этот отчёт не изменяет его статус.
