# Управление Vernatun Edge

## Где открыть

- Администратор платформы: **Vernatun Console → Управление Edge**, `/console/edge`.
- Администратор УК: **Vernatun OS → Управление Edge**, `/os/edge`.
- Используются существующие оболочка, авторизация, логотипы и API-клиент. Второе приложение или дублирующий пункт меню не добавлены.

## Два режима

**Платформа:** общий парк, организации, проекты, блоки, здания, состояния регистрации и WebSocket, версии, среда. Таблица показывает идентификатор, организацию, проект, привязки, heartbeat, очередь, устройства и последнюю синхронизацию.

**Организация:** только собственный парк. Карточки: узлы, online/offline, активные тревоги, устройства, последняя синхронизация. Глобальный выбор организации и управление машинными credentials не предоставляются.

Проект — введённое оператором название, а не новая сущность строительного проекта. Среда — явно заданная метка `unknown/test/staging/production`; она **не переключает API, базу, устройства или режим безопасности**. Существующим узлам автоматически не присваивается `test` по названию.

Числа из референсов не используются как данные. Фильтрация и пагинация выполняются API; размер страницы ограничен 100. Текущая реализация вычисляет статус из доступного парка на сервере до разбиения на страницы; это не нагрузочная сертификация большого парка.

## Создание и регистрация

1. Нажмите **Добавить Edge Agent**.
2. Укажите реальную организацию, Edge ID, имя и Site Code.
3. Выберите одно здание v1 либо существующий/новый блок v2 с его зданиями.
4. Выберите поддерживаемые конфигурационные модули и проверьте итог.
5. Система создаст **ожидающий регистрации узел**, не фиктивное online-подключение.
6. Нажмите **Сгенерировать токен** для этого узла. Сохраните одноразовый результат безопасно.

В ответе видны реальные Edge ID, имя, Tenant ID, Building ID для v1 либо Block ID и Building IDs для v2, Site Code, срок действия и одноразовый Bootstrap Token. Секрет не восстанавливается последующим GET-запросом. Повторная генерация отзывает прежние неиспользованные токены этого узла.

Для v1 предоставляется команда авторитетного `scripts/install.ps1`, включая поддерживаемый `-EdgeName`. Значения экранируются как литералы PowerShell. Для v2 экспорт подписан как конфигурация версии 2, а не выдается за совместимую команду v1.

Если создание блока прошло, а создание узла не удалось, повтор в том же открытом мастере использует уже созданный блок. Ошибка не скрывается.

## Карточка выбранного узла

- **Обзор:** состояние и реальные идентификаторы, привязки, последние данные.
- **Проверка соединения:** наблюдаемое состояние Cloud, регистрации, credential, WebSocket, heartbeat, очереди и потоков данных. Проверка фиксируется в аудите.
- **Здания:** разрешённые привязки v2. Одно здание v1 неизменяемо в этом интерфейсе.
- **Устройства:** профиль, здание, зона, состояние и последние отметки. Неизвестное состояние не превращается в offline.
- **Команды:** существующая история, исполнитель и результат; новая кнопка физического управления здесь не добавляется.
- **Тревоги и аудит:** доступные события с ограниченным объёмом ответа.
- **Конфигурация:** имя, Site Code, описание, проект/среда и интервалы; только изменённые поля отправляются в PATCH.
- **Безопасность/токены:** метаданные токенов; операции с credentials доступны только глобальному platform_admin.

Последние пакеты можно смотреть в человекочитаемом виде и как JSON. Нет искусственных событий Barrier-01, задержек или счётчиков. Пустые разделы честно показывают отсутствие данных.

## Блоки, архив и сохранность

**Настройки блоков** открывают компактный редактор названия, кода и допустимых зданий. Архивирование требует подтверждения. Блок с действующими узлами архивировать нельзя. Перенос состава блока с зарегистрированными узлами блокируется существующим контрактом; привязки узла v2 меняются отдельно.

Удаление узла — архивирование с сохранением истории, отзывом credentials и закрытием сокета. Восстановление не делает старый ключ действительным: требуется ротация. Удаление здания из узла запрещено, если на него уже ссылаются устройства, команды, события или тревоги.

## Загрузка и доступность

Парк обновляется каждые 30 секунд, выбранный узел — каждые 15. Сбой карточки не скрывает таблицу. Предыдущие данные сохраняются при ошибке обновления; ошибки API и топологии показаны отдельно. При смене контекста старые данные и одноразовые секреты очищаются.

На узких экранах парк представлен карточками; внутренние таблицы могут прокручиваться. Предусмотрены hy/ru/en, подписи контролов, фокус заголовка, клавиатура вкладок и модальные окна с возвратом фокуса.

## Выкатка в Coolify

Нужны **и frontend, и API из одной версии**, включая миграцию `043_edge_management_workspace.sql`. Одна замена frontend не исправляет отсутствующую серверную схему.

В API-контейнере после резервной копии и проверки правильной внешней базы:

```sh
cd /app
NODE_ENV=production corepack pnpm --filter @workspace/api-server run db:migrate:coolify:plan
```

Проверьте список pending и отсутствие drift. Затем в согласованное окно:

```sh
VERNATUN_COOLIFY_MIGRATION_CONFIRM=APPLY NODE_ENV=production \
corepack pnpm --filter @workspace/api-server run db:migrate:coolify:apply
```

Эта работа не запускает production-миграции, не меняет DNS и не отправляет команды реальным устройствам. Полная приёмка Windows Agent через production TEST-организацию остаётся отдельной проверкой. HTTP health и Cloud-диагностика сами по себе её не доказывают.
